OneApply — Technical PRD (MVP)

Updated July 29, 2026 | MVP | Shubham

Positioning: Apollo.io, but for job seekers instead of sales reps.

1. What is OneApply?

A Chrome extension + web dashboard that lets job seekers find, contact, and track recruiters. From a recruiter's LinkedIn profile: extract email (cache → pattern+verify → Apollo), draft a personalized email with the user's JD + best-matching resume, get user approval, send via Gmail, and monitor everything from an Apollo-style dashboard.

Core value: Better, more personalized recruiter outreach — with full visibility into who replied and who didn't.

2. The Five Pillars

  1. Email extraction from profile — cascade: PostgreSQL cache → pattern generation + verification → Apollo fallback.
  2. Automated email drafting with JD context → user approval → send — LLM drafts, user approves/edits, Gmail sends. No silent sending.
  3. Email tracking — every outreach persisted in Postgres, visible in the dashboard with status filters.
  4. Follow-up mailing on no response — background worker sends up to 3 AI-generated follow-ups every 3 days on the same thread.
  5. Notification system on response — Gmail polling detects replies → browser push + extension badge + dashboard inbox update.

3. Surfaces

Two UI surfaces from one shared React codebase:

  • Chrome extension (Manifest V3) — capture + approve + notify. Runs on LinkedIn profile pages.
  • Web dashboard (React SPA) — monitor + configure. Apollo-style tables, inbox, analytics, resume manager, settings.

4. How It Works (End-to-End)

  1. User visits a recruiter's LinkedIn profile.
  2. Clicks "Reach Out" in the extension.
  3. Extension reads name, headline, company, linkedin_url from the DOM.
  4. User pastes the JD and picks (or lets AI pick) a resume variant.
  5. Backend runs the email cascade: cache → domain resolve + pattern generate + verify → Apollo. Returns email + confidence.
  6. Backend calls LLM to draft the email (recruiter context + JD + chosen resume).
  7. Extension shows the draft to the user with Approve / Edit / Cancel.
  8. On approve, backend sends via Gmail API, persists outreach record with status sent.
  9. Every 5 min, reply worker polls Gmail; on reply → status replied → push notification + SSE to dashboard.
  10. Every hour, follow-up worker finds outreach where status ∈ {sent, followed_up}, last contact ≥ 3 days ago, follow_up_count < 3 → LLM drafts follow-up → sends on same thread. After 3 tries → status no_response.

5. MVP Scope

Building: extension, dashboard, Go backend, cascade email finder (pattern+verify+Apollo), Gmail send + poll, LLM drafting, resume matching, approval gate, auto follow-ups (3× / 3 days), reply notifications, 3 requests/day, LinkedIn only, Google OAuth login.

Not building yet: Google Sheets export, own email finder, sentiment analysis, multi-platform, multi-tenant, payment integration.

6. Tech Stack

  • Extension: Manifest V3, React + Vite + TypeScript, Tailwind
  • Dashboard: React + Vite + TypeScript, Tailwind, TanStack Query, TanStack Table
  • Backend: Go with Chi router, pgx for Postgres
  • Database: PostgreSQL 15+
  • Email finder: pattern generator + SMTP verifier + Apollo API (fallback)
  • Email sending / polling: Gmail API (OAuth 2.0)
  • LLM: Claude API (Anthropic SDK)

  • Realtime: Server-Sent Events for reply push
  • Hosting: Railway or Fly.io (Go binary + Postgres), dashboard served same-origin or via Vercel

7. Architecture — Layered, Interface-Driven

Every external dependency sits behind a Go interface so the concrete implementation can be swapped without touching business logic.

  • EmailFinder — orchestrated as a CascadeFinder{cache, domains, patterns, verifier, apollo}
  • DomainResolver — company name → domain
  • PatternGenerator — {name, domain} → candidate emails
  • EmailVerifier — candidate → deliverable/risky/invalid
  • EmailSender — Gmail today, SendGrid later
  • LLMService — Claude today, OpenAI later
  • OutreachRepo — Postgres, backs the dashboard
  • Notifier — browser push today, email digest later

8. Database Tables (MVP)

  • users — id (uuid), google_sub, email, name, gmail_refresh_token (encrypted), trial_ends_at, created_at
  • companies — id, name, domain, resolved_via (heuristic|clearbit), created_at, UNIQUE(name)
  • contacts — id, name, company_id (fk), email, linkedin_url, source (cache|pattern|apollo), verification_status (deliverable|risky|invalid|unknown), verified_at, fetched_at, UNIQUE(linkedin_url)
  • resumes — id, user_id (fk), label, storage_url, extracted_text, created_at
  • outreach — id, user_id (fk), contact_id (fk), resume_id (fk), job_description, email_subject, email_body, gmail_thread_id, status (pending_approval|sent|replied|followed_up|no_response|cancelled), sent_at, replied_at, follow_up_count (default 0), last_followed_up_at, created_at
  • replies — id, outreach_id (fk), gmail_message_id, from_email, snippet, body, received_at
  • notifications — id, user_id (fk), type (reply|quota|other), payload (jsonb), read_at, created_at
  • config — key, value (max_daily_requests=3, trial_days=3, follow_up_interval_days=3, max_follow_ups=3)

9. API Endpoints

Auth

  • GET /api/auth/google — start Google OAuth (login + Gmail scope)
  • GET /api/auth/google/callback — OAuth callback
  • POST /api/auth/logout
  • GET /api/auth/me — current user + quota

Outreach flow

  • POST /api/outreach/draft — {linkedin_url, name, company, headline, job_description, resume_id?} → runs cascade + drafts email → returns {outreach_id (status=pending_approval), contact, email_draft, resume_used, confidence}
  • POST /api/outreach/:id/approve — {edited_subject?, edited_body?} → sends via Gmail → returns {status: sent, gmail_thread_id}
  • POST /api/outreach/:id/cancel
  • GET /api/outreach — list with filters (status, company, date_from, date_to, search) + pagination
  • GET /api/outreach/:id — detail incl. reply thread

Contacts

  • GET /api/contacts — list with filters
  • POST /api/contacts/verify/:id — re-run verification

Resumes

  • POST /api/resumes — upload + label
  • GET /api/resumes
  • DELETE /api/resumes/:id

Analytics

  • GET /api/analytics?window=7d|30d|90d — sent/replied counts, reply rate, chart series, top companies

Notifications / Realtime

  • GET /api/notifications
  • POST /api/notifications/:id/read
  • GET /api/stream — Server-Sent Events channel (replies + quota events)

Settings

  • GET /api/settings, PATCH /api/settings

10. Email Finder Cascade (Pillar 1) — Detail

  1. Cache lookup in contacts by linkedin_url or (name, company_id). Return if found and verification_status ≠ invalid.
  2. Domain resolution: check companies. If miss → heuristic (Acme Corp → acme.com) with basic MX-existence check; if that fails → Clearbit-style lookup. Cache result.
  3. Pattern generation: build candidates from name + domain. Typical 6–8 formats: first.last, flast, first, firstl, lastf, first_last, last.first, firstlast.
  4. Verification: for each candidate, run SMTP handshake (connect → HELO → MAIL FROM → RCPT TO → check response code). Score: 250 → deliverable, 550 → invalid, timeouts/greylist → risky. Stop at first deliverable.
  5. Apollo fallback: if no deliverable pattern found → call Apollo. Verify the returned email too. Cache with source='apollo'.
  6. Failure: return email_not_found. Extension shows the user "we couldn't find this recruiter's email".

11. Draft → Approve → Send (Pillar 2) — Detail

  • Draft prompt to LLM includes: recruiter name/headline/company, user's JD, chosen resume's extracted text (or resume label if not parsed), user's own name/background.
  • Response constrained to {subject, body} JSON via tool use / structured output.
  • Outreach row created with status = pending_approval. No Gmail call yet.
  • Extension renders draft in an editable form. User can tweak subject/body.
  • On approve → POST /api/outreach/:id/approve sends via Gmail with final subject/body → status flips to sent, gmail_thread_id stored.
  • Pending drafts auto-expire after 24 h (cron sets status = cancelled) so they don't clog the dashboard.

12. Follow-Up Worker (Pillar 4)

Hourly cron. Query: WHERE status IN ('sent','followed_up') AND last_contact_at < now() - interval '3 days' AND follow_up_count < 3.

For each match: (a) check Gmail thread — if new reply, mark replied and skip. (b) else LLM generates follow-up (context: original email, previous follow-ups, JD, follow-up number). (c) Gmail sends on same thread. (d) increment follow_up_count, set last_followed_up_at. (e) If follow_up_count == 3, mark no_response.

13. Reply Notifications (Pillar 5)

Every 5 min, poll Gmail for messages on tracked thread_ids. On new inbound message: insert into replies, update outreach status, insert notifications row, broadcast on SSE stream, push a Chrome notification via the extension's service worker.

14. Risks

  • LinkedIn TOS: extension only reads visible DOM, no automated actions.
  • Gmail spam / reputation: 3 sends/day cap. Every email personalized. Explicit approval gate. Standard bounce handling.
  • SMTP verification accuracy: some providers (Google Workspace, Outlook) reject or catch-all all RCPTs → verification returns risky. Show confidence badge in the draft UI.
  • Apollo cost: cascade minimizes Apollo calls. Cache aggressively.
  • Cold email compliance (CAN-SPAM / GDPR): include opt-out line, physical address, honest sender identity. Legal review before v1.

15. Business Model

Free trial: 3 requests/day for 3 days. Then paid subscription (pricing + Stripe post-MVP). All limits configurable via config table.

16. After MVP (v2+)

Automated recruiter discovery, own email finder replacing Apollo, sentiment classification on replies, smart notifications (positive-only), multi-platform (Indeed, Glassdoor), resume auto-generation, team workspaces, Stripe integration, Google Sheets export.
